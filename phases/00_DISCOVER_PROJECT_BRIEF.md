# Stage 0A — 项目发现与项目简报

本阶段的完成范围与普通用户呈现遵守 `../references/ALPHA7_RUNTIME_INTEGRITY_CONTRACT.md`。默认 `CREATOR_SIMPLE`，不把后台 ID、Gate inventory 或整份机器状态倾倒给创作者。

用户使用中文时，本阶段的解释、提问和 `PROJECT_BRIEF_v0.1` 必须使用自然简体中文。技术 ID、规范枚举和状态码保持英文。不要再询问明显中文用户希望使用什么交互语言；只有角色台词、海外发行或多语言交付会实质改变项目时，才询问对应的语言字段。

## 进入条件

用于 `IDEA_ONLY`，或上游项目状态存在会影响后续决策的重要缺口时。

## 执行步骤

1. 提取用户已经提供的事实、限制和现有产物，不重复询问已知内容。
2. 普通、小型项目首轮最多问 3 个真正会改变路线的问题；其余未知项先保留，下一回合最多追问一个最高影响缺口。长项目、高风险项目或未知项很多时才使用 5–8 题深入口。每题理由压成一句，允许自由回答。
3. 生成 `PROJECT_BRIEF_v0.1`，按项目需要覆盖：
   - `project_route`：短片、长篇、纪录/非虚构、文化、科研科普、教育公益、品牌或展示，可组合；
   - `content_truth_mode` 与来源忠实要求：`FICTION / NONFICTION / MIXED`；
   - 用创作者原话保存的初始构想；
   - 现有文本、素材和资产；
   - 创意核心与不可妥协项；
   - 成功定义；
   - 目标受众假设；
   - 团队、时间、预算、技能与实际可用工具；
   - 形式、画幅、时长、连载方式和目标市场偏好；单条短片无需虚构季/集结构；
   - 参考作品中喜欢的部分与禁止模仿的边界；
   - 未知项、假设和最大不确定性；
   - 用户希望系统代为判断到什么程度；
   - `language_profile`：交互、创作产物、角色台词、供应商 Prompt 和发布文案分别使用什么语言。
4. 后台为关键字段标记 `USER_STATED`、`USER_APPROVED`、`PROPOSED`、`TEST_ASSUMPTION` 或 `UNKNOWN`。普通用户主视图只显示“已确定、我的建议、还没定”，不倾倒机器码。怀疑、歧义和缺失规则必须继续保持 `UNKNOWN`。
5. 从用户明确陈述的创意事实、受保护未知项和不可妥协项中建立 `core_claims`。
6. 只有简报仍含会改变后续路线的重要不确定性时，才请用户修正；不要为了形式完整反复追问。

非虚构与混合项目必须先登记已提供的来源产物。来源不齐不阻止形成简报，但相关事实保持 `UNKNOWN`，不得让模型用常识补齐引文、数字、文物细节、实验结论或人物身份。

## 关卡

把 `PROJECT_BRIEF_v0.1` 登记为 `artifact_class = TEXT_SPEC` 的项目简报产物。完成初步归纳后，它的 `artifact.status = SPEC_DRAFT`；只有重要用户事实已被忠实表达、关键来源与未知项已标清时，才可升为 `artifact.status = SPEC_READY`。不要为项目简报另造专用状态码。用户要求继续只允许流程前进，不代表批准简报中的 `PROPOSED` 字段。
